# AI 업무 프로젝트 템플릿 사용 안내

**이 `template` 폴더를 통째로 복사한 뒤, 업무에 필요한 요소만 남겨 사용합니다.** 자료 조사, 데이터 분석, 문서 작성, 발표, 개발, 자동화 등 여러 업무에 활용할 수 있습니다.

폴더명과 파일명은 영어이며, 설명은 한국어입니다. `1_README.md`는 안내서이며, `AGENTS.md`에는 사용자가 요청한 기록 문서 수정 규칙만 들어 있습니다. 나머지 MD 파일 6개는 내용과 양식이 없는 빈 파일입니다.

**기록 문서는 사용자 요청이 있을 때만 작성·수정합니다.** 작업 중에는 PROGRESS, 세션 전환 시에는 HANDOFF, 새 사실·교훈은 KNOWLEDGE_LESSONS, 필요한 메모는 NOTE, 실제 검증 결과는 VALIDATION이 담당하지만, 해당 상황이 생겼다는 이유만으로 자동 갱신하지 않습니다. 아래의 문서 역할·사용 시점 설명은 자동 작성 지시가 아닙니다.

이 템플릿은 전체를 복사한 뒤 업무에 필요한 폴더와 문서만 남겨 사용하는 기본 구성입니다.
참고자료·데이터·작업 중 파일과 핵심 코드·보조 코드·검증 증거를 구분해 관리합니다.
목표와 작업 규칙, 진행 이력, 지식·교훈, 인수인계와 검증 내용을 정리할 문서를 제공하며, 기록 문서는 사용자 요청이 있을 때만 작성·수정합니다.

## 1. 전체 구조

```text
template/
├─ 1_README.md
├─ AGENTS.md
├─ 2_PROJECT.md
├─ 3_PROGRESS.md
├─ 4_KNOWLEDGE_LESSONS.md
├─ 5_HANDOFF.md
├─ 6_NOTE.md
├─ 7_VALIDATION.md
├─ references/
├─ working/
├─ research/
├─ data/
│  ├─ raw/
│  └─ processed/
├─ src/
├─ scripts/
├─ tests/
└─ evidence/
```

`structure`는 이 템플릿을 보관하는 바깥 폴더입니다. 실제 업무를 시작할 때는 그 안의 `template`만 복사하고 프로젝트명으로 바꾸면 됩니다. `data/raw`, `data/processed`는 원본 데이터와 가공 데이터를 구분하기 위한 하위 폴더입니다.

빈 폴더에는 Git에서도 폴더를 보존할 수 있도록 `.gitkeep`을 넣었습니다. 구조도에서는 생략했습니다. 이 파일은 실행 파일이나 작업 지침이 아니며, 실제 파일이 생기면 지워도 됩니다.

## 2. 각 폴더의 역할과 사용 기준

아래의 “빼도 되는 경우”는 **새 업무를 시작하기 전 복사본을 정리하는 기준**입니다. 이미 자료가 들어 있는 폴더는 내용을 확인한 뒤 정리합니다.

| 폴더명 영어(한글) | 목적과 넣을 내용 | 사용할 때 | 빼도 되는 경우 |
| --- | --- | --- | --- |
| `references`(참고자료) | 제공받은 원본 자료와 업무 기준을 보관합니다. 요청서, 평가 기준, 기존 보고서, 참고 PDF, 양식 등을 넣습니다. | 외부에서 받은 자료나 요구사항 문서를 참고할 때 | 별도로 보관할 참고자료가 없을 때 |
| `working`(작업 중) | 임시 초안, 시안, 일회성 계산, 분류 전 메모 등 중간 작업을 보관합니다. | 임시 작업물이 생길 때 | 임시 작업물이 없거나 업무에서 지정한 다른 위치에서 관리할 때 |
| `research`(조사) | 직접 조사하며 만든 출처 목록, 조사 메모, 문헌 요약, 비교 분석을 관리합니다. | 자료 조사, 시장 조사, 논문 검토를 할 때 | 별도 조사 과정이 없을 때 |
| `data`(데이터) | 분석 입력과 가공 데이터를 함께 관리합니다. | CSV, Excel, JSON 등 데이터를 분석·정제·대조할 때 | 데이터 파일을 다루지 않을 때 |
| `data/raw`(원본 데이터) | 제공받거나 수집한 분석 입력 원본을 보관합니다. 가공본은 별도로 만듭니다. | 분석 기준이 되는 원본을 보관해야 할 때 | 데이터 자체를 쓰지 않거나, 원본을 외부 시스템에서 관리하고 접근 방법을 따로 기록할 때 |
| `data/processed`(가공 데이터) | 정제·병합·변환·집계한 중간 데이터를 보관합니다. | 원본을 가공해 별도 파일로 저장할 때 | 가공 데이터를 파일로 저장하지 않을 때 |
| `src`(소스 코드) | 직접 작성하는 프로그램과 분석 코드를 관리합니다. Python 파일, 노트북, 앱 코드 등을 넣습니다. | 코딩하거나 코드로 데이터를 처리할 때 | 코드 작성이 없는 업무일 때 |
| `scripts`(보조 스크립트) | 보고서·PPT·그래프 생성, 변환 등 핵심 기능 외의 작업 보조 코드를 관리합니다. | 산출물 제작이나 반복 작업을 돕는 코드가 생길 때 | 보조 코드가 없을 때 |
| `tests`(검증) | 반복 실행할 검증 코드와 작은 테스트 입력 자료를 관리합니다. | 기능, 계산, 데이터 변환 등을 반복 검증할 때 | 검증 코드를 만들지 않고 문서 검토·수동 확인만 할 때 |
| `evidence`(검증 증거) | 실제 출력, 기대값 비교표, 테스트 로그, 검토 기록을 보관합니다. 화면 증빙은 허용되는 환경에서만 수집합니다. | 정확성·동작·요구 충족을 근거로 보여줘야 할 때 | 다른 지정 위치에서 증거를 관리할 때 |

### 역할이 비슷해 보이는 폴더의 구분

문서·발표·최종 결과물 전용 폴더는 미리 만들지 않습니다. 결과물은 사용자나 업무 요구사항에서 지정한 경로에 저장하고, 별도 지정이 없으면 프로젝트 루트에 용도가 드러나는 파일명으로 저장합니다. `working`은 임시 작업물용으로 사용합니다.

- `references`와 `research`: 받은 참고자료는 `references`, 직접 조사해 작성한 메모와 출처 정리는 `research`에 둡니다.
- `references`와 `data/raw`: 요청서·설명 문서는 `references`, 계산·분석에 직접 넣는 원본 데이터는 `data/raw`에 둡니다. 같은 원본을 양쪽에 중복 보관할 필요는 없습니다.
- `tests`와 `evidence`: 검사하는 코드와 작은 입력 예제는 `tests`, 실제 실행·검토 결과는 `evidence`에 둡니다. `7_VALIDATION.md`에서 대상 요구사항·판정·증거 경로를 연결합니다. `tests`를 빼더라도 필요한 결과 검토는 수행합니다.
- `src`와 `scripts`: 최종 기능의 핵심 코드는 `src`, 그 결과를 보고서로 만드는 보조 코드는 `scripts`에 둡니다. 보고서 생성 자체가 제품의 핵심 기능이라면 해당 코드는 `src`에 둡니다.
- `scripts`와 `working`: 재사용할 보조 코드는 `scripts`, 버려도 되는 일회성 실험은 `working`에 둡니다. 결과 재생성에 필요한 코드를 임시 파일처럼 삭제하지 않습니다.

## 3. 각 Markdown 파일의 목적과 사용 기준

업무 지식과 레슨런을 함께 관리하도록 기본 문서를 `AGENTS.md`, `2_PROJECT.md`, `3_PROGRESS.md`, `4_KNOWLEDGE_LESSONS.md`, `5_HANDOFF.md`의 **5개**로 구성했습니다. `6_NOTE.md`는 메모·이해 정리, `7_VALIDATION.md`는 검증을 돕습니다. AGENTS는 도구의 기본 파일명에 맞춰 번호를 붙이지 않습니다.

| 파일명 영어(한글) | 목적 | 사용할 때·나중에 작성할 내용 | 빼도 되는 경우 |
| --- | --- | --- | --- |
| `1_README.md`(사용 안내서) | 구조의 이유와 각 요소의 역할, 정리 방법을 설명합니다. 현재 읽고 있는 문서입니다. | 템플릿을 가져와 필요한 요소를 선택할 때 참고합니다. | 구성을 익히고 정리를 마친 뒤 필요 없다면 삭제하거나 프로젝트 소개로 교체할 수 있습니다. |
| `AGENTS.md`(AI 작업 규칙) | AI가 따라야 할 반복 적용 규칙을 정합니다. | 쉬운 코드, 인코딩, 읽을 문서 순서, 원본 보존, 검증, 기록 갱신, 인수인계 규칙 | 별도 지침이 필요 없거나 기존 프로젝트 지침에서 관리할 때 |
| `2_PROJECT.md`(업무 정의·목표와 제약) | 무엇을, 왜, 어디까지 할지 정합니다. PRD 역할도 할 수 있습니다. | 문제·사용자·현재 업무, 목표·성공 기준, 포함·제외 범위, 제약, 입력 자료, 필수 산출물·경로, 미정 질문과 확인 답변 | 아주 짧은 업무이거나 다른 문서에서 같은 내용을 관리할 때 |
| `3_PROGRESS.md`(진행·업데이트 이력) | 변경과 판단의 누적 이력을 남깁니다. | 날짜, 변경한 파일·기능, 변경 이유, 목표·우선순위 변경, 검증 결과 위치, 남은 작업 | 다른 도구나 지정 문서에서 같은 이력을 관리할 때 |
| `4_KNOWLEDGE_LESSONS.md`(지식·레슨런) | 새로 확인한 사실과 경험에서 얻은 교훈을 한 문서에 모읍니다. | 지식: 용어·규칙·실무자 답변·출처·확정 사실과 가정. 레슨런: 잘된 점·실패·원인·다음 행동·재발 방지 | 같은 내용을 지정된 다른 문서에 관리할 때 |
| `5_HANDOFF.md`(인수인계) | 새 세션·다른 사람이 바로 이어받게 합니다. | 지금까지 한 것, 현재 상태, 결정사항과 이유, 남은 일, 주의점, 다음 첫 행동, 파일 위치·실행 방법 | 세션 전환·업무 인계가 전혀 없는 짧은 업무일 때 |
| `6_NOTE.md`(메모·이해 정리) | 자유로운 작업 메모와 본인의 이해를 정리합니다. | 아이디어·질문·설명 메모, 입력→처리→출력, 파일 역할, 구조 선택 이유, 실패 조건·영향. 확정한 사실·결정·검증은 해당 기준 문서에 반영 | 별도 메모가 필요 없거나 같은 내용을 다른 문서에서 관리할 때 |
| `7_VALIDATION.md`(검증 계획·결과) | 요구사항과 실제 검증 증거를 연결합니다. | 검증 대상, 기대 결과, 실제 결과, 통과·실패·미검증, 실행 방법, 증거 경로, 남은 한계 | 같은 내용을 다른 지정 문서에 기록할 때 |

`AGENTS.md`의 요청 기반 기록 규칙 외에는 작업 내용을 미리 채워두지 않았습니다. 위 표는 실제 업무에서 사용자가 작성을 요청했을 때 담을 내용을 설명한 것입니다. 빈 파일의 존재 자체가 작업이나 검증을 수행했다는 증거는 아닙니다.

`AGENTS.md`는 Codex의 기본 프로젝트 지침 파일명입니다. 실제 프로젝트에 복사할 때 기존 지침을 덮어쓰지 말고, 해당 프로젝트의 세션이 이 지침을 읽었는지 확인합니다. [OpenAI 공식 안내](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### 기록 문서를 작성·수정할 때의 공통 규칙

1. `3_PROGRESS.md`: 사용자가 요청하면 작업 중의 주요 변경과 이유를 기록합니다.
2. `5_HANDOFF.md`: 세션 전환·인계에 필요한 문서이며, 사용자가 작성을 요청했을 때 갱신합니다.
3. `4_KNOWLEDGE_LESSONS.md`: 새 사실·교훈이 생겼고 사용자가 기록을 요청했을 때 갱신합니다.
4. `6_NOTE.md`: 사용자가 메모를 요청했을 때만 사용합니다.
5. `7_VALIDATION.md`: 사용자가 기록을 요청하면 실제 수행한 검증 결과와 미검증 범위를 남깁니다.

작업 완료·세션 전환·사실 발견·검증 수행 자체는 자동 갱신 허가가 아닙니다. 필요한 작업과 검증, 채팅에서의 설명은 수행하되 기록 파일은 요청 없이 바꾸지 않습니다. 다른 파일에 자동 기록하는 방식으로 이 규칙을 우회하지 않습니다.

### 기록의 중복을 줄이는 예시

- “취소 주문은 집계에서 제외한다”는 확인된 업무 규칙 → `4_KNOWLEDGE_LESSONS.md`
- “취소 주문 제외 로직을 수정했다”는 변경 이력과 이유 → `3_PROGRESS.md`
- “취소 주문 2건 제외 여부를 기대값과 비교했다”는 검증 결과 → `7_VALIDATION.md`와 `evidence`
- “규칙 확정 전에 계산부터 구현해서 재작업했다”는 개선 교훈 → `4_KNOWLEDGE_LESSONS.md`
- “계산 수정은 끝났고 보고서 재생성이 남았다”는 최신 상태 → `5_HANDOFF.md`

같은 내용을 여러 문서에 반복하기보다 기준 문서와 파일 위치를 참조합니다. 작은 일반 업무에서는 필요한 기록을 한 문서에 통합할 수 있지만, 사용자가 요청한 5개 기본 문서는 템플릿에 모두 준비해 둡니다.

## 4. 업무 종류별 남길 요소 예시

아래는 시작할 때 참고하는 조합입니다. **표에 없는 요소도 필요한 이유가 있으면 남기고, 표에 있는 요소도 실제로 쓰지 않으면 빼면 됩니다.** README는 정리하는 동안 참고용으로 유지합니다.

기본 문서 5개는 공통 출발점으로 유지할 수 있습니다. 아래 MD 열은 업무별로 특히 자주 참조할 문서이며 전체 문서 목록은 아닙니다. 검증이 필요한 업무에는 `7_VALIDATION.md`와 `evidence`, 구조·한계 설명이 필요한 업무에는 `6_NOTE.md`, 보조 생성 코드가 생기면 `scripts`를 함께 남깁니다.

| 업무 종류 | 주로 남길 폴더 | 상황에 따라 더 남길 폴더 | 유용한 MD 파일 |
| --- | --- | --- | --- |
| 간단한 일회성 업무 | `working` | 받은 자료가 있으면 `references` | 목표 정리가 필요하면 `2_PROJECT.md` |
| 자료 조사·리서치 | `references`, `research` | 임시 초안이 생기면 `working` | `2_PROJECT.md`, `3_PROGRESS.md` |
| 데이터 분석·정제·대조 | `data` | 기준 문서가 있으면 `references`, 코드 분석 시 `src`, 반복 검증 시 `tests`, 검증 결과 보관 시 `evidence` | `2_PROJECT.md`, `3_PROGRESS.md` |
| 보고서·기획서·매뉴얼 | `references` | 조사 시 `research`, 수치 분석 시 `data`, 임시 초안은 `working` | `2_PROJECT.md`, `AGENTS.md` |
| PPT·발표·교육 자료 | `references` | 조사 시 `research`, 수치 분석 시 `data`, 제작 보조 코드가 있으면 `scripts` | `2_PROJECT.md`, `AGENTS.md` |
| 프로그램·웹 개발 | `src`, `tests` | 참고자료가 있으면 `references`, 데이터 처리 시 `data`, 보조 실행 코드가 있으면 `scripts`, 검증 결과 보관 시 `evidence` | `2_PROJECT.md`, `AGENTS.md`, `3_PROGRESS.md` |
| 반복 업무 자동화 | `src`, `scripts`, `tests` | 데이터 입출력 시 `data`, 검증 결과 보관 시 `evidence` | `2_PROJECT.md`, `AGENTS.md`, `3_PROGRESS.md` |
| 조사 → 분석 → 보고 → 발표 | `references`, `research`, `data` | 코드 처리 시 `src`, 반복 검증 시 `tests`, 임시 작업 시 `working` | `2_PROJECT.md`, `AGENTS.md`, `3_PROGRESS.md` |

개발 도구가 별도의 폴더 구성을 요구하면 해당 프로젝트 구조에 맞춰 조정합니다. 이 템플릿은 업무 정리를 위한 시작점이며, 특정 도구의 실행 환경까지 갖춘 프로젝트는 아닙니다.

## 5. 복사해서 사용하는 순서

1. **원본 `template` 폴더 전체를 원하는 작업 위치에 복사합니다.**
2. 복사한 폴더 이름을 실제 프로젝트명으로 바꿉니다. 예: `sales_analysis`.
3. 복사본의 `1_README.md`에서 각 요소의 역할과 업무별 조합을 확인합니다.
4. **복사본에서 불필요한 폴더와 빈 MD 파일을 삭제합니다.** 재사용할 원본 템플릿은 그대로 둡니다.
5. 목표·제약을 확인하고, MD 파일 작성이 필요하면 사용자가 해당 문서 작성을 요청합니다.
6. 참고자료와 데이터를 배치하고 작업을 시작합니다. 나중에 필요해진 폴더는 다시 추가해도 됩니다.
7. 검토한 결과물을 전달합니다. 기록 문서는 사용자가 갱신을 요청한 경우에만 수정합니다.

인수인계 작성을 요청하면 `5_HANDOFF.md`에, 새 사실·교훈의 기록을 요청하면 `4_KNOWLEDGE_LESSONS.md`에 정리합니다. 기본 문서는 사용자 요청에 따라 다른 지정 문서에 통합해 관리할 수도 있습니다.

이미 만든 프로젝트에 넣는 경우에는 복사본에서 필요한 구성만 남긴 후 그 내용물을 옮겨도 됩니다. 기존 파일과 이름이 같으면 내용을 확인하고 합치며, 무조건 덮어쓰지 않습니다.

### 예시: 코드로 데이터를 분석하고 보고서를 작성하는 업무

전체를 복사한 뒤 `research`, `working`을 뺀 예입니다. 이 업무에서는 반복 검증과 증거를 위해 `tests`, `evidence`를, 보고서 생성 보조 코드를 위해 `scripts`를 남겼습니다. 생성한 보고서는 사용자나 업무 요구사항에서 지정한 위치에 저장합니다.

```text
sales_analysis/
├─ 1_README.md
├─ AGENTS.md
├─ 2_PROJECT.md
├─ 3_PROGRESS.md
├─ 4_KNOWLEDGE_LESSONS.md
├─ 5_HANDOFF.md
├─ 6_NOTE.md
├─ 7_VALIDATION.md
├─ references/
├─ data/
│  ├─ raw/
│  └─ processed/
├─ src/
├─ scripts/
├─ tests/
└─ evidence/
```

이 예시보다 작은 업무라면 더 줄여도 됩니다. 필요한 요소만 남기는 것이 이 템플릿의 사용 방식입니다.

## 6. AGENTS.md의 현재 규칙과 추가 규칙 예시

**현재 AGENTS.md에는 기록 문서를 사용자 요청이 있을 때만 작성·수정한다는 규칙이 들어 있습니다.** 아래의 코드·인코딩 등은 추가 규칙을 작성할 때 참고하는 예시입니다. 별도 요청 없이 AGENTS에 모두 채워 넣은 상태는 아닙니다.

### 쉬운 코드와 작업 원칙

- 다른 사람이 이해하고 수정할 수 있는 간단한 코드와 명확한 이름을 사용합니다. 필요 이상으로 추상화하거나 새 도구를 도입하지 않습니다.
- 작업 전 목표·제약·완료 기준과 관련 자료를 확인합니다. 중요한 미정 사항은 질문하고, 영향이 작은 가정은 명시합니다.
- 구현·문서 작성 후 실제 결과를 확인합니다. 수행하지 않은 검증을 완료했다고 기록하지 않습니다.
- 사용자가 기록을 요청하면 주요 변경은 `3_PROGRESS.md`, 새 사실과 교훈은 `4_KNOWLEDGE_LESSONS.md`에 정리합니다.
- 사용자가 인수인계를 요청하면 `5_HANDOFF.md`를 갱신합니다. 다음 세션은 관련 문서와 실제 파일을 확인한 후 이어갑니다.
- 여러 작업을 나눠 맡길 때는 담당 범위·입력·출력·완료 기준을 정하고, 동시에 같은 파일을 수정하는 충돌을 피합니다.

### 인코딩 문제를 줄이는 규칙

- 새 텍스트·Markdown·코드 파일은 프로젝트가 다른 형식을 요구하지 않으면 UTF-8로 읽고 저장합니다.
- 기존 파일은 인코딩·BOM·줄바꿈 형식을 먼저 확인하고 보존합니다. 알 수 없는 파일을 임의로 UTF-8로 해석해 덮어쓰지 않습니다.
- Python 등에서 파일을 읽고 쓸 때 인코딩을 명시합니다. UTF-8 BOM 입력처럼 확인된 형식에 맞춰 처리합니다.
- CSV는 제출 규격과 사용 도구가 요구하는 인코딩을 따릅니다. 모든 CSV에 BOM을 붙이거나 제거하는 식으로 일괄 변경하지 않습니다.
- 터미널 표시 문제와 파일 내용 손상을 구분합니다. 화면에서 깨져 보인다는 이유만으로 원본을 다시 저장하지 않습니다.
- 저장 후 다시 읽어 한글·특수문자·대표 데이터가 유지됐는지 확인합니다. 문서 산출물은 가능한 경우 실제 파일을 열거나 렌더링해 확인합니다.

이 규칙은 오류 가능성을 줄이기 위한 원칙이며, 선언만으로 인코딩 문제가 자동 해결되지는 않습니다.

## 7. HANDOFF와 세션 전환

`3_PROGRESS.md`는 누적 이력, `5_HANDOFF.md`는 **가장 최근의 이어받기 안내**입니다. 사용자가 인수인계 작성을 요청하면 전체 대화를 복원하지 않고도 진행할 수 있게 다음 내용을 기록합니다.

1. 지금까지 완료한 것과 실제 파일 경로.
2. 현재 작동하는 범위와 마지막 검증 결과.
3. 중요한 결정사항과 이유. 긴 근거는 해당 문서 위치를 참조.
4. 남은 일과 우선순위, 다음에 바로 할 첫 행동.
5. 알려진 오류·미확인 사항·주의점.
6. 필요한 실행 방법, 작업 디렉터리, 데이터 기준 버전. 비밀키·비밀번호는 기록하지 않음.
7. 마지막 갱신 시점과 실제 파일 상태.

컨텍스트가 가득 차서 중요한 조건을 잃기 전, 또는 단계가 끝나는 시점은 사용자가 인수인계 작성을 요청하기 좋은 때입니다. 그 시점이 왔다는 이유로 AI가 문서를 자동 수정하지 않습니다. 고정된 비율이나 “반드시 새 세션”을 규칙으로 삼지 말고 남은 시간·대화 상태·작업 단위를 보고 판단합니다.

새 세션은 `AGENTS.md`, `2_PROJECT.md`, `5_HANDOFF.md`를 우선 확인하고 필요한 `3_PROGRESS.md`, `4_KNOWLEDGE_LESSONS.md`, 검증 결과를 읽습니다. 문서와 실제 파일 상태가 다르면 차이를 알리고, 기록 문서 수정은 사용자가 요청했을 때만 수행합니다. 경로를 적는 것만으로 자동 세션 연결이 되는 것은 아닙니다.

## 8. 일반 업무의 진행 흐름

1. **요구사항 확인**: 업무 목적, 제공 자료, 결과물 형식과 저장 위치를 확인합니다. 기존 프로젝트의 안내서와 작업 규칙을 먼저 읽습니다.
2. **범위 결정**: 불명확한 조건을 확인하고, 필요한 기능과 제외할 범위, 완료 기준을 정합니다.
3. **작업 분배**: 구현·분석·검토·전달에 쓸 시간을 나누고, 위임할 작업의 입력·출력·제약을 정합니다.
4. **작은 결과부터 확인**: 입력부터 결과까지 이어지는 최소 흐름을 만들고, 기대 결과와 실제 결과를 비교한 뒤 확장합니다.
5. **결과 검토**: 요구사항 충족 여부, 예외 상황, 파일 내용과 실제 동작을 확인합니다. 확인하지 못한 부분과 남은 한계를 알립니다.
6. **전달·인계**: 사용자와 정한 위치·형식으로 결과물을 전달하고 필요한 사용 방법을 설명합니다. 인수인계 문서 등 기록 파일은 사용자가 요청한 경우에만 작성·수정합니다.
